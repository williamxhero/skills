# CPA profile for `merge-upstream-parents`

Use this profile only for an explicitly selected CPA workflow or requested CPA-specific steps. Follow the [canonical skill](../SKILL.md) for scope, identity, pins, candidate, promotion and any push. Profile selection alone adds CPA maintenance checks, not a release, push or deployment. It does not change the merge root. For CPA scripts, verify the workspace containing the selected CPA checkout(s) and `ops/`; take its path from the user or the selected checkout, and do not assume one. It contains four fork checkouts and the self-owned CPA-Qwen; a parent merge leaves CPA-Qwen alone.

## CPA maintenance

- Use [CPA repository notes](repositories.md#parents-and-remotes) for expected mappings and exclusions. The cached [inventory script](../scripts/inventory.ps1) may supplement discovery (`-Root <workspace>`; omit `-Fetch`): it uses hard-coded tracking refs and is not authority for ancestry, GitHub identities or publish targets. Its legacy `-Fetch` fetches/prunes broadly; use the canonical named-head fetch instead.
- Apply the [CPA conflict playbook](merge-playbook.md), including protected paths and byte-exact `README-source.md` handling. Use the [CPA checks](repositories.md#verification-commands) for affected packages and UI. When claiming a vet failure is inherited, reproduce it on the pinned parent; do not suppress a fork regression.
- Manager's `providers/opencode-go` is a separate vendored source, not a GitHub parent of Manager. If subtree sync is requested (including a full CPA sync that explicitly includes vendored sources), use the [subtree notes](repositories.md#vendored-provider-subtree-manager-only) in the isolated candidate before final verification. Otherwise report that it was not part of the parent merge.

## Version only when authorized and applicable

Do this in the candidate before final verification if the user requested CPA version/release work or the selected repo's merge policy requires regeneration. For composed versions, refresh the source part from the newest valid parent tag reachable from the pinned parent. If the shipped behavior changed but that tag did not, bump the own part once (`-BumpEx patch` unless a different increment is required). One bump per requirement, not per review round. Preserve CPA-Qwen's standalone version unless it is separately in release scope.

- Read `ops\update-versions.ps1` in the verified CPA workspace for the `Source`, `Generated` and `Kind` of the selected repo. It writes `VERSION` and the generated Go constant together; never hand-edit `version_generated.go` or keep upstream's version identity.
- The script resolves hard-coded tracking refs and names the child by directory. Use a private staging workspace with a standalone checkout of the reviewed candidate under the expected child name. Bring over the reviewed `VERSION` and generated file if they are still staged in the candidate. In the standalone checkout only, map the pinned parent SHA to the exact tracking ref expected by the script and obtain the necessary reachable tags from the verified parent (no tag overwrites; stop on conflicts or unverifiable tags). Confirm the tracking ref equals P and `git describe --tags --abbrev=0 <source-ref>` selects the intended parent tag. Never change shared tracking refs or import broad tags into the live checkout just to satisfy this script. Stop if the script's default-source mapping does not fit the requested source.
- Run `& <CPA-workspace>\ops\update-versions.ps1 -Root <staging-workspace> -Repository <child>` (add `-BumpEx patch` in that same run if needed). Verify with the same `-Root` and `-Repository` plus `-Check`. Review and copy **only** the generated version outputs back to the candidate. Include them in the merge or an allowed release follow-up on the candidate; confirm the shipped version changed where required and verify the final candidate. Report `-Check` results for the selected repositories; a different, unmerged repo may legitimately mismatch its current parent ref.

## Package and deploy only when requested

A requested CPA deployment must have a known target and a verified candidate promoted by the canonical skill. Do not infer push permission from a deployment request. For a stack deploy, account for every required component: stop if any required repo is blocked or if the deploy tool could pick stale/unverified artifacts. Build only approved changed artifacts using the [build and artifact notes](repositories.md#builds-and-artifacts); ensure the staged version, source SHA and hash match the verified checkout. Keep tracked build outputs under review (especially the two Manager panel copies).

- For the verified local Windows target (本机), review the [local deployment entry point and artifact selection](repositories.md#local-deployment-windows), then run the documented scheduled task from the CPA workspace. Check the [receipts, hashes, service/port health and logs](repositories.md#post-deploy-verification), including the version in the built artifact and the running process path/start time.
- For any other named target, follow the [other-device prerequisites](repositories.md#other-devices) and confirm access, layout, services and rollback before packaging/transferring. Do not reuse the local task. If no target is known, ask rather than choosing one.

Report any authorized version, subtree, package or deployment results alongside the canonical per-repo report; include the target, deployed version, artifact hashes and health evidence for a deployment.
