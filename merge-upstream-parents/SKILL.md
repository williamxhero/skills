# Merge upstream parents

A plain merge updates an eligible local branch only. Push only if the user authorizes it or explicitly selects an applicable workflow that includes it. Version edits require applicable repository policy and authorization (a requested release/version workflow or required merge-time regeneration within scope). Packaging and deployment require a separate explicit request or an explicitly selected deployment workflow and a known target. Use Git and `gh`; report missing access or tooling instead of falling back to browser/GUI automation.

**CPA only:** Read the [CPA profile](references/cpa-profile.md) when the user explicitly selects it or requests CPA-specific work such as CPA versioning or deployment. A CPA path alone does not select it or authorize release actions. The profile adds project-specific checks to the steps below; it does not replace them.

## 1. Establish scope

- Start at the requested path, or the session's working directory if omitted. Resolve the path and run `git -C <path> rev-parse --is-inside-work-tree --show-toplevel`. Compare canonical filesystem paths; success alone does not mean this directory is a root. Use the containing root for a single-repo request from a subdirectory. An explicit grouping request instead uses the named directory as the container, even when it lies inside a repository. A bare repository is not a worktree. Resolve interfering `GIT_DIR`, `GIT_WORK_TREE` or similar overrides before trusting discovery.
- For group discovery, list **immediate directories only**, including hidden entries. A `.git` directory **or file** is a candidate; verify the child's own top level equals that child. Report invalid markers. Skip symlinks/junctions and registered submodules (check the containing repo for a `160000` index entry) unless explicitly in scope. Flag multiple worktrees sharing the same canonical `git rev-parse --path-format=absolute --git-common-dir` rather than merging them twice. Do not recurse into non-repo directories or into the children of candidates. List the container separately; do not merge it as a child.
- If scope is implicit: a non-repo directory is a group; a worktree path without immediate repo candidates means its containing repo. At a worktree root **with** immediate repo candidates, check the container's identity (step 2). Use a confirmed non-fork with no declared parent as the container. If the root is also eligible, its identity is unresolved, or the path is a subdirectory inside a checkout with immediate candidates of its own, ask which checkout(s) to merge. Block a bare repo or broken checkout supplied as a merge target. An explicitly scoped single repo does not trigger child discovery; report an empty group rather than searching deeper.

**Done:** every in-scope checkout has an inventory row, or scope is blocked with a specific question. A per-repo blocker need not stop other unambiguous rows.

## 2. Identify the fork, its parent, and the branches

1. List remotes and inspect their effective fetch and push URLs separately (`git remote get-url --all <remote>` and `git remote get-url --push --all <remote>`). Resolve GitHub HTTPS/SSH aliases to host and `owner/repo`; compare canonical repository IDs on the same host, not URL spelling, a remote name, a tracking branch, or the active `gh` account. Do not expose URL credentials in the report.
2. Query each plausible identity explicitly, e.g. `gh api --hostname <host> repos/<owner>/<repo>`; read `id`, `full_name`, `fork`, `parent`, `default_branch`, and the clone URLs. Identify the local checkout by a unique, supported mapping to a GitHub repo (e.g. one remote for the fork and another for its API parent). A lone parent remote with no evidence of which fork the checkout belongs to does not establish its identity. If several identities remain plausible, ask for the exact repo instead of guessing. For a GitHub fork, use the API's immediate `.parent`, not `.source` or a remote called `upstream`; query the parent itself to verify its identity and default branch. A successful `fork: false` for the identified checkout with no verified project-declared parent is **no parent**. Missing `.parent` on a fork, failed API access (including 404) needed to resolve the mapping, and ambiguous remotes are **unresolved**, not no-parent results.
3. Use the fork default branch for the local target and its own remote head; use the parent default branch for the source. Report both, even if the names differ. Nonstandard mappings (a non-default branch or an upstream not represented by a GitHub fork link) require an explicit repository and exact `refs/heads/...` from the user or an explicitly selected documented mapping. Verify repository identity, relationship (GitHub or authoritative project/user declaration, plus shared Git history), and the named ref. Report an explicitly requested custom upstream as such; never silently substitute it for the GitHub parent or infer it from tracking config.
4. Record verified fork and parent fetch endpoints, even if a matching named remote is absent. Check URL rewrites (e.g. `git ls-remote --get-url -- <url>`); they must still resolve to the verified repositories. For an authorized push, also identify a remote with exactly one effective push URL belonging to the **fork**, distinct from the parent by repository identity. A remote with multiple push URLs, mismatched fetch/push identities, an unverified alias, or a mirror is not a safe push target. Resolve or report it; a verified local-only merge does not require a writable push target.

**Done:** each eligible row has verified identities, exact source/target heads and endpoints; the other rows say no parent or name the unresolved evidence.

## 3. Gate and pin

- Require a clean worktree and index, including untracked files and submodule state (`git status --porcelain=v1 -uall --ignore-submodules=none`). Check for an in-progress merge, rebase, cherry-pick, revert or bisect (use `git rev-parse --git-path` for operation markers). Require an existing local target branch and an attached, born HEAD. Check repository instructions and `git worktree list --porcelain`: if another worktree holds the target, the checkout cannot safely switch to it, policy blocks the local update, or another process is writing, stop that row. Leave existing changes alone. Record the original branch/HEAD and the target tip **B**.
- Fetch **the exact branch heads**, each to its own new run-scoped ref. Substitute full refs (`refs/heads/<branch>`) and use a unique run ID per repository. For example, in PowerShell:

  ```powershell
  git -C $repo fetch --no-tags --no-prune --no-prune-tags --no-recurse-submodules --no-write-fetch-head --no-auto-maintenance -- $parentUrl "${parentHead}:refs/merge-upstream-parents/$run/parent"
  git -C $repo fetch --no-tags --no-prune --no-prune-tags --no-recurse-submodules --no-write-fetch-head --no-auto-maintenance -- $forkUrl "${forkHead}:refs/merge-upstream-parents/$run/fork"
  ```

  Require each fetch to succeed, then resolve each destination with `git rev-parse --verify '<run-ref>^{commit}'` and record the full SHAs **P** (parent) and **F** (fork remote). `git ls-remote --exit-code --refs -- <url> <exact-head>` can distinguish missing heads (exit 2) from transport failure. A failed fetch does not license reuse of an old ref. Neither `git fetch origin main` nor a successful tag-only fetch proves `origin/main` advanced. Merge by SHA, not `FETCH_HEAD`, a tag, or a mutable remote-tracking ref.
- Test `git merge-base --is-ancestor F B` (local includes the fork's remote tip) and `git merge-base --is-ancestor P B` (local includes the parent). Exit 0 means yes, 1 means no, other exits are errors. In shallow (`git rev-parse --is-shallow-repository`) or incomplete history, deepen or complete the necessary history through verified endpoints within scope, then re-pin/recheck before trusting negative results or using a merge base. If that is not possible, report a blocker. If B is behind or diverges from F, stop; fork-side reconciliation is separate. If P is an ancestor of B, report **up to date**. Otherwise require a verified shared merge base. For counts, `git rev-list --left-right --count B...P` gives local-only then parent-only commits.

**Done:** B/F/P and ancestry are recorded, or the row has a no-op or blocker. Treat P as a snapshot; do not substitute a newer parent tip mid-run.

## 4. Build and verify an isolated candidate

1. Create a unique local branch in a separate worktree (`git worktree add -b <sync-branch> <new-path-outside-checkouts> B`). In that worktree merge P with `git merge --no-ff --no-commit --no-autostash --no-overwrite-ignore --no-rerere-autoupdate P` so even a trivially fast-forwardable parent can be reviewed before commit. Keep the target untouched while resolving.
2. Read local maintenance instructions at B and inspect changes on both sides of the merge base. Review cleanly merged paths as well as conflicts against B: preserve the fork's README and translations, branding, project policy, and other local contracts. Integrate compatible upstream improvements; record intentional changes to protected paths. Avoid choosing an entire side in bulk. If maintaining both intents requires a product or policy decision, leave the candidate for review.
3. Review the staged diff, clear all unmerged entries (`git ls-files -u`), and check for whitespace errors and conflict markers (`git diff --cached --check` plus a marker scan of changed files). Apply any authorized profile/version steps in isolation. Commit the reviewed merge without bypassing hooks. Run the affected build/tests and policy checks on the final candidate (including fork regressions and relevant new parent tests); recheck the clean candidate and verify that **C**, its final SHA, contains both B and P. If any required check fails or cannot run, leave the candidate for handoff and keep the target unchanged.

**Done:** C is clean, reviewed and verified, or the report records the candidate path, failing gate and next decision. Do not reset, stash, clean, rewrite history, force-push, or forcibly remove anyone's worktree or branch.

## 5. Advance and report

- Immediately before promotion, recheck target tip B, original branch/HEAD, worktree cleanliness, policy/operation gates, and the fork remote head F (`ls-remote`). If anything moved or is dirty, stop and keep C; do not reuse C against a changed base. If switching is needed, use `git switch --no-guess --no-overwrite-ignore <target>` and confirm HEAD is clean and still at B on the intended branch. Advance with `git merge --ff-only --no-autostash --no-overwrite-ignore C`. A fast-forward isn't a lock against concurrent writers; if the branch or worktree cannot be held stable, leave C for handoff. Verify the target ref equals C, P is its ancestor, and the checkout is clean. Restore the original branch after a switch only if it still exists at its recorded tip and the switch is safe; otherwise report the current branch.
- For an authorized push only, recheck applicable branch rules and direct-push permission, the effective push URLs, target ref and remote SHA. Push **one** full refspec (`<C>:refs/heads/<fork-branch>`) to the verified fork remote with `--no-follow-tags --recurse-submodules=no`, no force, mirror, broad refspecs or unexpected configured push options. On a blocked branch, permission failure or rejected push, report the local result and the remote blocker; do not bypass checks or switch destinations. Verify the fork's exact remote head with `ls-remote` after success.
- Report each row: path, fork and parent/branches, B/F/P and C when known, status (**merged**, **up to date**, **no parent**, **skipped/blocked**), protected changes, checks, and whether a push was authorized and verified. Include retained candidate locations and the precise error or question for blocked rows. Include version/deployment results only if applicable.
