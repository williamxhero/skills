# One-line summary

只回答两行：这次会话交付了什么，以及它创建或关闭了哪个 issue。内容全部来自本次会话能核实的证据；会话里没有的事不补、不猜，也不去翻别的 issue 凑数。

## 输出

```text
<一句话：本次会话交付的功能或结果>
<issue 行>
```

- 第一行一句话，说清用户拿到什么；跟随用户本轮的语言，中文不超过 60 字，不换行、不列清单、不写文件路径、命令和分支名。
- issue 行只写本次会话**创建或关闭**的 issue：每个写成 `#{号码} {标题}`，可用「创建」「关闭」前缀区分，多个用「；」隔开。一个都没有就写 `未创建也未关闭任何 issue`。
- 除这两行外不加开场白、结论或细节；用户追问再展开。

## 取证

1. 先对齐本次会话自己的证据：用户请求、工具结果、`git log`／`git status`、构建或部署结果。第一行的每个动作都要能指回其中一条，不把计划、别人的提交或上一次会话的成果算进来。
2. issue 只统计本次会话真实创建或关闭的：
   - 会话里出现创建／关闭动作或编号时，用 `gh issue view <号码> --json number,title,state` 回读标题和状态，标题以回读为准。
   - 本次会话没有碰 issue，就不要查、不要造，直接写「未创建也未关闭任何 issue」。
   - 回读失败时写「无法确认 issue 状态（原因）」，不写推测的标题。
3. 测试、构建、部署只有本次会话确有证据才写；不确定就省略。
4. 上下文已被压缩、看不出做过什么时，先从会话文件、`git log`、工作区状态复原主线；复原不了的如实写「本次会话没有可核实的产出」。

## 怎么算「功能」

- 用户能看到或被改变的能力、行为、部署结果才算；纯排查、清理、重构也照实写它的结果。
- 同一件事的多个步骤压成一句；不同任务用「另完成 …」并进同一句，用户要求拆开才分行。
- 用结果说话，不写过程：写「新增复制路径按钮并把合并后的主干部署到 30141」，不写「读了 FileViewer、改了 4 个文件」。

## 不许做的事

- 只读：不创建、不关闭、不评论 issue，也不提交、推送或部署。
- 不把没做完的写成做完；不把「合并了分支」写成「功能上线」，除非本次真的部署并验证过。
- 不输出第二段总结、不附 issue 链接列表、不复述工具调用。

**完成标准：** 两行符合上述格式；第一行每个动作都能指回本次会话证据；issue 行有编号＋回读标题，或明确写了没有。

## 例子

有 issue：

> 为文件预览工具栏增加了复制完整路径按钮，并把合并后的主干构建部署到 30141。
> 创建 #{42} 文件预览支持复制路径；关闭 #{38} 工具栏缺少路径入口

没有 issue：

> 本次会话只做只读排查，没有改动代码，也没有交付功能。
> 未创建也未关闭任何 issue

## 用完回看，值得就改自己

在给出这两行之后，花几句复盘本轮：哪里被用户纠正、哪一步把旧会话或别人的提交算进了本次成果、哪个 issue 编号／标题没回读就写了。

- **够格才写。** 换成相近任务还会再犯，并且能写成一句「看到什么就做什么」的可执行约束。偶发环境故障、本轮专有数据、没验证的猜测、已有规则已经覆盖的内容都不写。
- **写进本技能。** 优先并进已有的输出契约、取证步骤或停止规则，其次才加一条；同一教训再出现就改结构，不再堆句子。被本轮证伪的旧要求删掉，不留互相矛盾的条目。
- **只动本次实际加载的那份技能。** 改它的 `SKILL.md` 或随本目录交付的 references；它由别的工具管理时（例如 CC Switch 的管理副本），改维护源并说明这次改动未安装，不覆盖管理副本。固定上游／专项资产只改 adapter，不改原文件；不搬别处的规则，不新增第二套权威，不写密钥或私人路径。
- **不改本轮结论。** 复盘不追加授权：不自行提交、推送、安装、部署，也不改写已交付的证据。
- **没有就 pass。** 不改文件，不造变更记录，不涨版本号。收尾最多一句「已沉淀：…」或「无沉淀」，不复述复盘过程。
