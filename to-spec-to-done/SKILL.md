# To Spec To Done

每次进入先完整读取随本目录分发的[共享工程规则](references/engineering-quality.md)和[自动推荐 grilling 适配](references/auto-grilling.md)，按其中的定位规则解析依赖。缺失或不可读即报告 blocked，不使用记忆中的近似版本。

唯一的 SPEC 生成入口是 `to-spec` 技能：读取实际已安装的 `SKILL.md` 及触发的必需参考，并执行其流程。本技能只提供前置设计、规格组织和交付要求，不复制其模板、不自行代行发布。

## A1 调查现状

读取项目指令、相关实现和测试、既有 SPEC／tickets、术语、ADR 与经验；核对 tracker、标签和发布授权。区分事实、已有决定、假设与未知。完成条件：能说明现在怎样工作、本次改什么、不改什么，以及哪些事实需要进一步调查；关键依赖缺失按共享规则报告 blocked。

## A2 每次必执行 grilling

读取实际 `grilling/SKILL.md`，按已加载的自动推荐适配执行。小而明确或信息完整的需求同样必跑；依 frontier 调查事实、推荐、在授权内自动采用全部推荐，再重算下一轮。复用已有决定和已授权的公开测试接口（seam），不重复访谈或常规确认；满足 [`codebase-design` 共享触发条件](references/engineering-quality.md#codebase-design)时，直接读取并应用实际 `codebase-design`；仅按共享规则的专属条件触发 `design-an-interface`／`domain-modeling`。完成条件：影响当前规格的设计分支均已处理，重要未知有明确处理方式；无法查明的关键事实保留 blocked。

## A3 检查开工就绪

逐项使用共享工程规则检查目标／非目标、模块职责、接口、状态权威与写入、成功／失败／恢复、兼容、可观测性、测试和验收。核对实际设计结论：调用者必须知道什么、复杂度集中在哪里、怎样经公开接口验证、为何不选更简单方案。适用结论写入原 SPEC 的实施／测试决定，不另建设计文档；纯措辞且无这些判断可简记不适用。完成条件：没有阻止首个可验收切片实施的未决事项；尚可调查则回 A2，无法验证的关键事实或缺少授权则 blocked，不以自动推荐掩盖。

## A4 规格组织

- **单个 SPEC**：简单需求能在一个清楚的范围内描述并验收时，只发布一个 SPEC，无需另建总 SPEC，也无需为了形成清单强拆。
- **多个 SPEC**：确有必要按独立目标或验收边界拆分时，发布多个子 SPEC，以及一个汇总完整目标和整体验收的总 SPEC。子 SPEC 是规格；实现 tickets 仍在后续通过 `/to-tickets` 拆分。
- **总 SPEC todo list**：在总 SPEC 正文用 Markdown 复选框列全子 SPEC 的标题和真实链接／Issue 编号，并说明已确定的依赖。规格发布时完成子 SPEC 的创建或复用及清单回填；未验收的项保持未勾选，新增、移除或替换子 SPEC 时同步更新。
- **GitHub relationships**：使用 GitHub Issues 时，必须同时通过原生 sub-issues relationship 将所有子 SPEC 挂到总 SPEC；已确定的阻塞依赖使用原生 issue dependencies。正文引用不能替代系统关系，CLI 不支持时使用 GitHub API。

## A5 委托 to-spec

读取并执行实际 `$to-spec`，使用其原模板（七节），由它独占生成和发布。包装器只在本入口适配篇幅：User Stories 和验收覆盖各项独立需求，不设数量／篇幅配额，不重复同义条目；不修改原技能。传入原始需求、事实与已有决定、grilling 已采纳决定、假设、测试接口与验收、规格组织及以下交付要求：

- 将设计结论放回原模板的实施决定、测试决定、非目标和进一步说明。沿用已授权的推荐和测试接口，不重开同一轮确认；新实质变化先按授权处理。
- 保持原模板的实现路径／代码限制及原型决策例外；必需执行入口用可从实际安装定位的技能标识，不作为实现路径移除，也不写个人绝对路径。当次精确路径和命令放绑定提交的执行记录。
- 首次发布前，将下方“执行与交付”原样完整写入**每个新 SPEC** 的正文，包括独立 SPEC、子 SPEC 和总 SPEC；只写在总索引或最终回复不算完成。
- 已有明确拆票结果的遗留 SPEC 沿用原 tickets 及依赖，不补交付段落、不重新拆票；有总 SPEC 时仍核对其清单和原生关系。
- 创建前搜索并回读同范围已有 SPEC，按目标、验收和已有任务图核对身份，复用合格 Issue；标题相似不足以判断同一任务。只补齐本范围缺项，不接管无关关联、不盲目重复写入。
- 按项目指令显式指定 tracker（GitHub CLI 指定仓库、API 使用对应 endpoint），不从当前目录猜目标；发布时应用 `ready-for-agent`。

完成条件：由 to-spec 发布或复用的真实 SPEC 引用已取得，具备 A6 回读所需身份；本地草稿或聊天文本不是已发布。读取缺失、发布无权或 tracker 不可达时保留草稿／已发布成果，报告 blocked，不代行 to-spec。

## A6 回读核验与恢复

通过 tracker 工具、CLI 或 API 源头回读每个 SPEC 的正文、验收、关键设计决定、完整交付段落及 `ready-for-agent` 标签，不能只相信创建响应。多 SPEC 同时核对：总清单标题与真实链接、未验收项未勾选、原生子 Issue 集合、每个子 SPEC 的父 Issue，以及阻塞依赖方向。CLI 不支持原生关系时使用实际 GitHub API 并回读；正文链接不替代原生关系。

创建或关系写入超时、结果未知时，按共享恢复规则先搜索并回读 Issue 及关系，再决定是否重试。重复运行复用已有 Issue 和有效关系；不属于当前范围的既有关联先确认归属，不能擅自删除／改挂。不完整时仅在授权内补缺并再次回读；若发布／关系失败或无权，保留实际成果并报告未完成、具体阶段和最小恢复条件，不因已有正文清单宣称成功。

完成条件：所有规格正文、验收、标签、交付要求、总清单及必需原生关系一致，并有源头回读证据；单 SPEC 不制造多余总索引或关系。

## A7 报告并停止

报告实际 SPEC 链接、创建／复用结果、组织方式、关键决定与假设、回读证据和限制；仅在 A6 全部满足时声明规格发布完成。阻塞时报告真实阶段和保留成果，不宣称 Done。

本入口到此结束，不启动 `/to-tickets`、`$implement-spec`、编码、实现工作树、Git 集成／清理／push 或 Issue 关闭。交付段落只是后续约定，不是本次实施授权。已授权外层入口如需继续，由外层接收这些 SPEC 引用后主持；本入口不递归启动架构扫描。

## 写入 SPEC 的“执行与交付”

> 本 SPEC 发布并回读后停止；发布不等于实施授权。另行获得实施授权后，由 `/skill:implement-spec-to-done` 主持完整交付：由它委托 `to-tickets` 拆分具有明确依赖的 tickets，并委托 `implement-spec` 隔离实施与集成；两者不是替代入口。按实际安装解析技能，按项目指令显式指定 tracker。
>
> 实现及适用测试通过后，先将 ticket 成果汇入 SPEC 集成分支（B5）；集成后的候选经最终独立审查（B8）及验收（B9）通过后，再合入主干，运行合并后验证。仅清理本任务明确归属、成果已纳入主干且工作树干净的 worktree 和对应分支。正常 push 主干，源头核对实际远端、本地主干与 tracking ref 一致。完整交付后写入并回读完成记录，再先关闭 tickets、后关闭 SPEC，并回读关闭状态。任一必需项失败则停止后续交付，保留成果并报告阻塞；不强删或强推。
