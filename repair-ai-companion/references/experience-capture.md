# 修复研究经验记录规范

在每次 `$repair-ai-companion` 运行开始时完整读取本文件。它定义独立“研究过程经验总结”的筛选、记录和关闭标准。

## 双文档边界

- 事故账本记录本次发生了什么：稳定 ID、时间线、症状、假设、owner、commit、部署和重测状态。
- 研究经验总结记录以后如何更好地修：意外发现、失败路径、正确 seam、可迁移规则、适用边界和验证证据。

不要把原始日志复制到经验总结，也不要用经验总结替代事故账本。

## 建立文件

在项目本地 `.scratch/ai-companion-repair/` 建立独立文件：

`<YYYY-MM-DD>-<目标时点或简短主题>-research-lessons.md`

保持本地、不自动提交；只有项目规则或用户逐文件授权时才提交。文件首部写用户目标、事故范围和“只收录已验证经验”的约束。

## 何时追加候选

出现以下任一情况时立即追加，不等任务结束：

- 观察推翻了高概率假设。
- 一个中间状态看似成功，但用户可见结果失败。
- 修复落在与最初判断不同的 owner 或 seam。
- 临时恢复方式会破坏审计、事实时点、幂等或权限边界。
- 主路径通过但重试、恢复、缓存、降级或发布旁路失败。
- 不可控依赖暴露了新的重试、替代、排队或 fail-close 要求。
- 一条规则可以跨时点、任务或 owner 复用，并且已有验证证据。

普通命令、一次性环境路径、未经验证的猜测和只对当前机器有意义的细节不进入经验总结。

## 条目模板

```markdown
## <可复用结论>

### 观察证据

<真实现象、稳定 ID 或测试；避免凭据和大段日志>

### 失败路径

<先前做法为何不足；没有失败路径时写“无”>

### 可复用经验

<用命令式、可执行语言说明以后应怎样做>

### 适用边界

<适用于哪些阶段、owner、数据或故障；哪些情况不适用>

### 本次落地与验证

<代码 seam、测试、commit、部署和真实重测证据>
```

先写候选状态；验证完成后补充“本次落地与验证”。验证推翻候选时保留原观察，并明确标记“不成立”及反证，避免事后改写研究过程。

## 提炼标准

一条经验只有同时满足以下条件才进入最终摘要：

- 具体：能改变下一次 agent 的动作或验收方式。
- 可迁移：不依赖单次随机值或当前机器偶然状态。
- 有证据：至少有 trace、红绿测试、故障注入、发布探针或真实重测之一。
- 有边界：说明何时适用，避免把局部现象升级成全局规则。
- 单一来源：不与事故账本或 SKILL.md 重复整段事实。

## 关闭检查

关闭修复前：

1. 回看事故账本中的每个已关闭问题，确认都评估过是否产生经验候选。
2. 合并语义重复条目，保留证据最强、边界最窄的版本。
3. 删除凭据、个人敏感信息、无价值原始日志和未验证断言。
4. 确认经验总结含最终 commit、测试、安装/部署及真实重测证据。
5. 在最终回复提供经验总结的绝对路径链接，并概括本次新增的 3–7 条最高价值经验。
