# 修复 AI 伴生

把当前任务当作总控。持续执行“记录问题 → 红色复现 → 按 owner 修复 → 回归测试 → 发布安装 → 真实重测”，并同步沉淀经过验证的研究过程经验，直到用户指定的 AI 伴生请求交付完整、合格的最终回复。

## 结果契约

以用户可见结果为终点。消息已接收、批次 `completed`、模型调用成功、流式输出开始、占位句出现或后续研究任务创建，都不代表完成。

只有同时满足以下条件才结束：

- 真实的新请求已经通过产品的正式 Exchange/UI 路径提交；历史正式记录保持不可变。
- AI 已交付用户实际要求的数据、判断和自然语言正文，而不是“我会查询”“稍后继续”或故障说明。
- 依赖该回复的研究、认知、工具和发布任务均已终止；不存在无人领取的 `pending`、遗留 lease 或未完成 follow-up。
- 每个已观察问题都有正确 seam 上的红→绿回归测试；不可控故障有经过故障注入验证的重试、替代来源、排队恢复或诚实降级机制。
- 修复已进入实际运行版本；源码测试通过但未安装、未部署或未进行真实重测，不算完成。

## 1. 建立事故账本

先读取目标仓库的 `AGENTS.md`、产品原则、`CONTEXT.md` 和相关 ADR。遵守消息不可变、事实时点和正式周期隔离。

在 `stock_advisor/.scratch/ai-companion-repair/` 建立本次事故账本和独立研究过程经验总结。开始修复前完整读取 [研究经验记录规范](references/experience-capture.md)，按其命名建立 `*-research-lessons.md`；两份文档保持本地，除非项目规则或用户明确授权，不纳入 Git 提交。

事故账本逐项追加：

- 用户目标与目标时点
- cycle、message、batch、job、attempt、tool trace 等稳定标识
- 发生时间、观察时间、精确症状和当前阶段
- 可重复的红色命令或测试
- owner、对应 GitHub issue、修复任务 ID、commit 和部署版本
- 重测结果，以及该问题为何不会以同类形式复发

记录事实后再修改。保留历史条目；用追加状态关闭问题，不改写先前观察。

研究经验总结与修复同步更新。每当假设被推翻、owner/seam 改变、主路径与旁路语义不一致、不可控依赖暴露新容错要求，或发现可跨任务复用的验证方法时，立即追加候选；验证后补充适用边界、落地 seam 和证明。不要等到最终回复才凭记忆回写。

## 2. 监督真实链路

从 `%LOCALAPPDATA%\AITradingCompanion` 的 Exchange、Runtime 数据库、工具审计、MemoryHub 回执和已安装 build 信息重建时间线。只通过产品正式 interface 触发新请求；直接写业务 SQLite 只能用于隔离测试数据库，不能用于修复生产状态或制造成功。

每轮至少检查：

1. 客户端命令是否进入 Exchange 并被确认。
2. message/batch 是否持久化，批次状态是否符合真实交付阶段。
3. cognition/research job 是否创建、领取、续租、重试和结束。
4. Provider Broker 调用是否有合格上游结果。
5. WAG 与各 tool 是否取得带来源、事实时点和 schema 验证的证据。
6. 最终消息是否通过资格门并投影到客户端。
7. 是否残留 pending job、错误完成状态或只说不做的占位回复。

在工作持续期间每 60 秒内给用户一次有变化的简短进度。使用 `wait_threads` 跟踪委派任务；采用最新 cursor，避免重复播报无变化快照。

## 3. 每个问题执行红→绿闭环

对每个新症状执行以下循环：

1. 捕获真实失败证据，脱敏所有认证材料。
2. 建立快速、确定性、agent 可运行且能命中用户症状的反馈循环。
3. 给出 3–5 个可证伪假设并按概率排序；继续验证，不等待用户确认。
4. 把最小复现写成修复前失败的回归测试。
5. 确认 owner，按下一节路由修复。
6. 先跑针对性测试，再跑 owner 工程的完整验证。
7. 部署或安装包含修复 commit 的实际版本。
8. 用全新请求重测原场景；若出现下一个问题，将其追加到账本并开始下一轮。

每轮结束时同时评估该问题是否产生可复用经验。即使没有，也在事故账本中记为“无新增经验候选”，保证每个问题都经过评估。

一次暂时成功不能关闭故障类别。用回归测试覆盖原始模式；对网络、超时、路由、重启和数据源故障增加故障注入测试。涉及恢复与并发时，至少再验证一次重启恢复或幂等重跑。

## 4. 按 owner 开独立任务

调用本 Skill 即代表用户授权为以下 owner 创建独立 Codex 任务。先用 `list_projects` 找到保存的项目；Git 仓库默认使用隔离 worktree。每个 owner 同时只保留一个修复任务，后续同 owner 问题追加给该任务，避免重复并发写入。

### Provider Broker

当证据表明失败位于 provider 路由、上游选择、模型资格、超时、503/429、输出 schema 或 Broker 重试时，在 `provider_broker_proj` 对应项目创建任务。通常路径为 `D:\WILL\AGENT\provider_broker_proj`。

任务必须包含原始脱敏 trace、红色复现、回退路由要求、测试、部署和生产探针。要求修复任务完成其工程内的实现、验证、合并与必要部署，并回传 commit、版本和验收证据。

### WAG

当证据表明失败位于网页搜索、网页读取、浏览器出口、抓取、代理、结果为空或 WAG API 时，在 `web_access_gateway_proj` 对应项目创建任务。通常路径为 `D:\WILL\TOOLS\web_access_gateway_proj`。

要求任务验证真实出口和搜索/读取结果，并覆盖超时、无结果、代理故障、恢复与替代路径；需要生产生效时部署到实际服务并验证。

### AI 伴生 tools

当失败位于 Tool Manager、tool manifest、adapter、MarketHub/行情调用、数据 schema、时点验证或工具路由时，在 `stock_advisor` 项目创建独立工具修复任务。工具任务使用隔离 worktree；总控任务继续拥有产品编排逻辑，避免两个任务修改同一文件。

工具开发员必须主动补足替代能力：优先建立有序 adapter 路由、第二独立数据渠道、结果缓存与事实时点验证；不能只让故障 provider 当前恢复后就关闭任务。

### stock_advisor 产品逻辑

总控任务直接修复队列领取、状态机、完成语义、消息发布、任务恢复、资格门、UI 投影和跨 owner 编排。若与工具任务文件范围重叠，先等待工具任务完成并集成，再修改。

委派任务提示必须要求：读取本工程规则、先红后绿、不做生产数据热补丁、保留失败证据、提交可集成 commit，并以对应工程真实生产验收为终点。

### 委派任务归档

维护本次修复流程创建的任务清单。每个任务在总控完成以下验收后，立即调用 `set_thread_archived` 主动归档：

- 已读取其最终回复及 commit、测试、部署或生产探针证据；
- 结果已被总控集成，或已明确判定无需集成；
- 没有待处理问题、审批、用户输入或返工；
- 任务 ID 和归档时间已追加到事故账本。

仍在运行、等待输入、需要返工或尚未完成集成验收的任务保持未归档。归档只作用于本次 Skill 创建的任务，不处理用户既有任务或其他任务。

## 5. 外部故障的稳健性标准

外部服务失败时，产品继续解决用户目标，同时保持事实诚实。不得编造行情、来源或已完成状态，也不得把首次“不可用”故障说明当作最终答复。

根据故障类别至少实现并验证一种主恢复路径和一种保底路径：

- Provider：独立上游路由、限定次数重试与退避、熔断后换路、可恢复队列。
- 搜索/WAG：替代搜索或直接来源 adapter、空结果判定、不同出口、后续自动补查。
- 行情/工具：MarketHub 之外的独立数据渠道、官方收盘缓存、来源最终性与时点校验。
- 产品层：保留未完成批次、自动领取与重放、使用带年龄标记的冻结证据先给有用部分、恢复后追加完整结果。

当实时外部信息确实无法取得时，回复应使用已经验证且仍适用的证据，明确数据时点和未知项，并给出不依赖虚构数值的条件式判断；后台继续有界恢复。所有来源均失败且任务核心价值无法兑现时，保持任务未完成并继续修复容错链，不能用一条“服务不可用”消息结案。

## 6. 集成、发布与真实重测

等待所有 owner 任务完成并检查其测试、commit、部署与生产探针。将修复按依赖顺序集成到各工程默认分支；遵守各仓库提交和推送边界。

对 `stock_advisor`：

1. 运行针对性测试和 `scripts/test.ps1`。
2. 构建并安装 Windows exe。
3. 核对已安装 `build-info.json` 指向修复 commit 且不是 dirty build。
4. 重启产品/Runtime，验证 orphan lease、pending job 和自动恢复路径。
5. 对正式周期先用隔离 preview/frozen replay 验证，不重写历史结果。
6. 再通过正式 Exchange/UI 提交一条全新、同意图的真实消息并持续监督。

最终语义验收从用户原话推导。以“盘后回顾”为例，至少核对目标交易日、主要指数、成交/市场宽度、板块或主题、用户实际持仓、风险与下一交易日条件、来源和资料时点；缺失项必须诚实标记，不能被空泛文字替代。

## 7. 关闭门

关闭前逐项证明：

- 事故账本中的每个问题均有 owner、修复和验证结果。
- 原始红色复现已转绿，新增回归测试和 owner 全量测试通过。
- Provider/WAG/tool 的不可控失败已通过故障注入证明可切换、可恢复或可提供有用降级。
- 已安装/已部署版本与修复 commit 一致。
- 新的真实请求产生完整最终回复；批次只在最终回复后完成。
- 数据与文字满足用户目标，证据时点正确，没有伪造或遗漏核心范围。
- 同类错误没有在最终 trace 中再次出现；无调试 instrumentation 和临时生产补丁残留。
- 本次修复流程创建且已完成验收的所有委派任务均已主动归档，归档记录已写入事故账本。
- 独立研究过程经验总结已完成去重和证据核验；每个已关闭问题都已评估经验候选，最终回复提供该文件链接。

任一项不满足就继续下一轮，不输出“已解决”。只有需要新凭据、新权限、不可逆操作或用户才能决定的产品语义时才暂停并请求用户。
