# 任务过程提炼检查表

本参考用于把复杂来源任务转成证据充分的新 Skill。简单任务不需要机械填写所有表格，但所有质量门槛仍然适用。

## 1. 来源任务契约

先冻结来源范围：

| 字段 | 内容 |
|---|---|
| 来源任务 | 当前任务、当前对话中的明确片段，或可唯一定位的其他任务 |
| 用户原始目标 | 用户真正要求的结果，不是执行者后来选择的手段 |
| 授权范围 | 允许读取、写入、下载、外部交互和清理的边界 |
| 交付物 | 文件、代码、配置、数据、报告或外部状态 |
| 验收标准 | 能独立区分成功和表面成功的检查 |
| 成功证据 | 实际命令输出、结构检查、测试、媒体探测、数据校验等 |

如果“交付物”或“成功证据”为空，默认不创建正式技能。

## 2. 证据账本

对影响最终决策的事件填写：

| 顺序 | 尝试或观察 | 可见结果 | 证据强度 | 后续影响 |
|---|---|---|---|---|
| 1 | 做了什么或看到了什么 | 原始错误、状态或交付物 | 直接 / 间接 / 推测 | 保留、改写为 fallback、丢弃 |

证据强度：

- **直接**：工具输出、文件检查、测试、校验器或页面可重复状态；
- **间接**：改变一个关键变量后现象稳定改变，但根因未被完全隔离；
- **推测**：只有相关性或记忆，没有可验证材料。

正式技能的硬门槛只能来自直接证据。间接证据可形成有条件的诊断建议；推测不得写成规则。

## 3. 失败因果卡

每个拟保留失败都回答：

```text
尝试：
可观察现象：
排除了什么：
根因证据：
使结果改变的动作：
解决后验证：
适用症状：
是否进入主流程：否；应进入预检、fallback、停止条件或故障矩阵
```

以下情况不要写成“根因”：只看到 HTTP 200；只看到某个工具无报错；同时改变了多个变量；成功 URL 或令牌具有短时效；错误只发生一次且无法复现。此时使用条件化措辞，并保留重新诊断入口。

## 4. 保留与删除规则

| 材料 | 默认处理 | 例外 |
|---|---|---|
| 最终成功所需的非显然步骤 | 保留在核心流程 | 若已有必需 Skill 完整覆盖，则引用依赖 |
| 能提前阻止昂贵失败的检查 | 前移为预检 | 检查成本高于失败成本时改为 fallback |
| 已验证的错误恢复 | 放入症状驱动 fallback | 只能恢复一次性故障时标注环境范围 |
| 失败工具或接口 | 放入故障矩阵 | 若完全无诊断价值则删除 |
| 视频 ID、PID、日期、端口、临时目录 | 参数化或删除 | 协议固定值且确为不变量时保留 |
| cookies、密钥、完整签名 URL、个人信息 | 删除 | 无例外；仅说明需要哪类授权或公开来源 |
| 用户特定目录和服务名 | 默认参数化 | 属于明确环境 Skill 的稳定约定时标注范围 |
| 偶发点击、拼写错误、探索性打印 | 删除 | 暴露通用陷阱时抽象为一条检查 |

## 5. 从实际时间线到最优流程

按以下顺序重排：

1. **入口与适用范围**：什么请求应触发，哪些相似任务不应触发；
2. **前置条件**：权限、身份、输入、依赖、目标目录和可用工具；
3. **低成本预检**：尽早发现身份错误、数据为空、目标歧义和磁盘问题；
4. **首选路径**：实际被证据证明有效的最短步骤；
5. **症状驱动 fallback**：只在明确现象出现时启用，不按历史顺序盲试；
6. **完整性门槛**：拒绝 HTTP 200、非空文件、退出码 0 等表面成功；
7. **原子完成与清理**：partial、临时资源、失败恢复和防覆盖；
8. **完成报告**：交付物、指标、验证、限制和实际使用的身份或工具。

最优流程应比原始探索过程更短，但不能删掉使成功可复现的关键条件。

## 6. 目标 Skill 质量门槛

完成前逐项回答“是”：

- 描述能准确触发目标任务，并排除相邻但不同的任务吗？
- 主流程来自已验证成功路径，而不是事后猜测吗？
- 每个重要失败都变成了预检、fallback 或停止条件吗？
- 已经证明无效的路线是否离开了主流程？
- 环境特例是否标注了适用范围？
- 一次性值是否参数化，敏感值是否完全移除？
- 验证能拒绝表面成功和残缺交付物吗？
- 重试、外部写入和清理是否有边界？
- `SKILL.md` 是否简洁，条件性细节是否按需放入 references？
- 所有脚本、链接、YAML 和结构验证是否真实通过？

任一关键项为“否”时继续修正，不发布技能。

## 7. 示例：抖音下载过程

调用：

```text
将本次抖音视频爬取 $process-to-skill : DY视频下载
```

应提取的证据类别包括：目标视频与输出文件被精确识别；Edge UI 显示名和底层 profile 目录的差异得到只读核对；官方下载入口不支持；播放器 `currentSrc` 为 `blob:` 但同一元素的 `<source>` 暴露公开签名媒体地址；媒体经无 cookies 的普通 GET 落盘；最终由 `ffprobe` 验证时长、分辨率和音视频流。

由此合成的主流程应是“核对浏览器身份 → 锁定当前视频 → 读取公开媒体源 → partial 流式下载 → `ffprobe` 验收 → 原子改名”，而不是依次重放所有失败的 API、第三方解析器和下载工具。失败路线应沉淀成症状表，例如“HTTP 200 空响应不是成功”“工具要求 fresh cookies 时不得导出 cookies”“`blob:` 需要继续检查同一播放器的 `<source>`”。具体视频 ID、签名 URL、PID 和单次文件大小不应进入通用 Skill。
